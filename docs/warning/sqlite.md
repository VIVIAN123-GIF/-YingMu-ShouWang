# 待优化问题清单（仅存，当前代码可正常运行，后续出问题再修改完全来得及）
## 一、高优先级（业务联调大概率踩坑，出现报错优先改这3条）
1. Observation表 `extra_metadata` 字段与Pydantic别名冲突
   - 问题：数据库列名metadata、ORM字段extra_metadata，读写容易匹配失败
   - 触发场景：新增/查询观测数据、前端回放接口
2. 各模型内SQLAlchemy Enum在SQLite无效
   - 问题：存入非法字符串不会拦截，会破坏状态机判断
   - 触发场景：算法/前端传错来源、风险域、等级字符串
3. 多对多关系默认`lazy="selectin"`异步性能差，存在N+1查询
   - 触发场景：批量查询风险事件、批量导出周报数据

## 二、中优先级（不崩溃，但不符合冻结接口规范、后期难维护）
1. 全部DateTime字段未存储时区，不满足ISO8601规范
   - 规范要求：时间必须带时区，当前仅存本地时间
   - 触发场景：跨时段统计、多日趋势周报
2. `evidence_ids`/`observation_ids` 使用逗号文本存储数组
   - 问题：查询、删除关联数据极不方便，已做多对多中间表但遗留冗余字段
   - 处理：新业务完全不用这两个字段，只使用risk_event_evidence关联表
3. 风险域、风险等级、来源模式等字符串硬编码分散各处，无统一常量文件
   - 触发场景：全局修改枚举文字、新增风险分类时需要批量改代码

## 三、低优先级（纯代码规范美化，不影响任何功能）
1. 表关系反向命名不统一（obs_list / intervention_list 命名风格杂乱）
2. SystemConfig的config_value未统一JSON序列化存储，读取需区分数字/字符串/布尔
3. CRUD Update模型字段过多，缺少批量更新封装函数
4. init_db无开关控制是否删除旧数据表，反复测试不方便
5. 索引、唯一约束缺少注释，新人看不懂设计意图

## 补充说明
1. 当前代码执行建表脚本完全正常，能支撑接口、算法联调，上面所有问题**不会阻断现阶段开发**；
2. 只有当对应业务场景出现报错、逻辑异常、性能卡顿，再按清单对应条目修改即可；
3. 所有修改不改动数据表核心字段结构，不会破坏现有存储数据。
