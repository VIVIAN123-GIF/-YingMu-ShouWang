# 萤石 H.264 实时取流恢复验证

验证日期：2026-08-24

## 结论

此前所谓“重复短片”不是摄像头实时视频，也不是已经确认的 CDN 缓存问题。设备主、子码流均为
H.265 时，萤石标准流和实时播放地址返回固定的 H.264 编码不兼容提示视频。该提示视频固定为
约 7.5 秒、15 帧，因此不同时间录制得到相同文件和 SHA-256 是预期现象。

将设备主码流和子码流切换为标准 H.264 后，官网标准流以及后端实际使用的
`/v2/live/address/get` 均恢复真实连续视频。后端联调主路径固定使用 HTTP-FLV，HLS 保留为已通过
的兼容性路径。

## 设备配置

| 项目 | 切换前 | 切换后 |
|---|---|---|
| 主码流 | 标准 H.265（`videoCode=5`） | 标准 H.264（`videoCode=1`） |
| 子码流 | 标准 H.265（`videoCode=5`） | 标准 H.264（`videoCode=1`） |
| 后端直播协议 | 历史临时使用 HLS | `EZVIZ_LIVE_PROTOCOL=4`（HTTP-FLV） |
| 媒体模式 | VIDEO | `YINGMU_CAPTURE_MEDIA_MODE=VIDEO` |
| 采集窗口 | 历史为 4 至 8 秒 | `YINGMU_VIDEO_CAPTURE_SECONDS=15` |

设备编码切换后已通过开放平台设备信息接口确认在线。主、子码流不得在后续联调前切回 H.265。

## 后端接口验证

两组测试均由仓库验证脚本调用后端生产路径使用的 `/v2/live/address/get`，请求通道 1、流畅
子码流，并由 FFmpeg 录制为临时 MP4。报告不保存 Token、设备序列号或完整播放地址。

| 协议 | HTTP / 业务码 | 录制时长 | 帧率 | 帧数 | 结果 |
|---|---|---:|---:|---:|---|
| HTTP-FLV（4） | `200 / 200` | 15.0 秒 | 10.0 FPS | 150 | `LIVE_DEVICE / SUCCESS` |
| HLS（2） | `200 / 200` | 15.0 秒 | 约 9.93 FPS | 149 | `LIVE_DEVICE / SUCCESS` |

HTTP-FLV 私有复核录像的画面时间从 `22:36:15` 连续推进至 `22:36:27`；HLS 私有复核录像
从 `22:39:37` 连续推进至 `22:39:49`。两者均为真实摄像头画面，不再出现编码不兼容提示片。

## 验收口径

- HTTP-FLV 是后端告警视频采集的冻结主路径。
- HLS 已通过一次兼容性补测，但不阻塞 HTTP-FLV 联调。
- 本次只证明设备到后端媒体采集恢复；真实告警触发、算法输出、Evidence、RiskEvent 和 Agent Job
  仍需在后续端到端联调中分别验收。
- 哈希相同只能证明字节相同，必须结合实际画面、时间戳、时长和帧数判断媒体是否实时。
