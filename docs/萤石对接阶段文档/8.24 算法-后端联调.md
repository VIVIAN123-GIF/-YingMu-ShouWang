建议按这个顺序进行：

1. **固定设备配置**

保持主码流和子码流为 H.264，不再切回 H.265。记录本次根因：

```text
重复短片实际为萤石返回的 H.265 不兼容提示视频；
切换主、子码流为 H.264 后，标准流恢复正常。
```

2. **验证后端实际取流接口**

分别对 `/v2/live/address/get` 的 HTTP-FLV 和 HLS 各测试一次。优先使用 HTTP-FLV，因为它已经在官网标准流中验证成功。

验收标准：

- 接口业务码为 `200`；
- FFmpeg 能录制至少 10～15 秒；
- 录像是摄像头真实画面；
- 时间戳连续递增；
- 不再出现固定提示片；
- 视频帧数正常，而不是之前的 15 帧。

只要 HTTP-FLV 成功，后端正式联调就可以固定使用：

```text
EZVIZ_LIVE_PROTOCOL=4
YINGMU_CAPTURE_MEDIA_MODE=VIDEO
```

HLS 可以作为兼容性补测，不需要阻塞后续联调。

3. **完成一次真实告警端到端验证**

启动三个后端终端：

- API 服务
- Alarm Worker
- 临时 webhook 通道

在萤石平台更新当前有效回调地址，然后让授权人员在摄像头范围内正常走动，不需要模拟跌倒。触发后继续保持画面约 10 秒。

需要检查：

- webhook 是否收到告警；
- 原始告警是否写入数据库；
- Worker 是否创建并消费任务；
- 是否取得真实视频；
- 证据文件是否可播放；
- 算法任务状态是否成功或进入待处理状态；
- 风险事件与证据关联是否正确。

4. **与算法同学联调**

把本次真实 H.264 视频作为输入样本，验证：

- 后端向算法提交的视频不是提示片；
- 算法能够读取 H.264 MP4/FLV；
- 返回结果符合约定的数据结构；
- 后端能够落库算法分数、标签和状态；
- 算法失败、超时和重试路径可观测。
